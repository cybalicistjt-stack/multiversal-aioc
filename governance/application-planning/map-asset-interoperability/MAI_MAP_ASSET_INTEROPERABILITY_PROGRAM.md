## Resolved MAI-06 contract

### Adapter selection

An explicitly requested adapter ID must resolve exactly and cannot be overridden by detection. Without a pinned adapter, registered detectors execute deterministically in stable adapter-ID order and exactly one strong match is required. Multiple matches produce `ambiguous-adapter`; no match produces `unsupported-source`. MAI never guesses a provider.

### Provider adapters

The framework is provider-neutral. The bounded proof set is `tiled-json`, `ldtk-json`, and `foundry-scene-json`, reflecting source classes already surveyed in MAI-01. Those adapters may understand provider-specific versions and fields, but their schemas remain translation boundaries and never become canonical Multiversal map truth.

### Mapping and preservation

Adapters map only explicit source semantics into completed MAI-02..05 presentation contracts. Every import carries externally supplied source reference, SHA-256 checksum, license evidence, permission matrix and import lineage. Permissions are never inferred from file contents. A raw source snapshot and all unmapped/vendor-specific fields remain preserved with deterministic diagnostics rather than silently discarded.

### Partial and unsupported sources

Missing optional data, unsupported provider features, dangling source references, and incomplete packages produce explicit deterministic diagnostics. No asset, semantic requirement, permission, compatibility, substitution, owner identity or runtime state is silently invented. Automated cross-pack substitution remains MAI-07.

### Deterministic receipt

The adapter ID/version, source checksum, normalized mapping summary and ordered diagnostics produce a stable platform-identical MAI-06 import receipt. The receipt proves translation behavior; it is not a license grant or owner-domain mutation receipt.
