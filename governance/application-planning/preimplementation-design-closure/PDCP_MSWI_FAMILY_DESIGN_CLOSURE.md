# PDCP — MSWI Family Design Closure

**Project:** PDCP — Preimplementation Design Closure Project  
**Family:** MSWI — Multiversal Systemic Worldplay Integration  
**Status:** DESIGN_CLOSED_FOR_FAMILY_REDUCTION  
**Date:** 2026-09-16  
**Implementation authority:** none  
**Historical baseline:** 18 planned tranches  
**Reduced implementation/proof plan:** 7 tranches

## 1. Closure result

MSWI remains necessary, but its baseline roadmap mixed three different kinds of work:

1. genuinely unique cross-system worldplay integration;
2. specialist capabilities that belong to existing owner families; and
3. generic execution/authoring/analysis infrastructure already assigned by PDCP to GPR, MRCS, PCA, ARI, MCS, MSAS and canonical owner operations.

PDCP therefore reduces MSWI from 18 standalone tranches to seven implementation/proof tranches while preserving every accepted capability.

The surviving implementation seams are:

1. `MSWI-01` — Systemic Transformation State & Integration Core;
2. `MSWI-03` — Cross-System Consequence Routing, Recovery & Domain Adapter Runtime;
3. `MSWI-04` — Ecology Succession, Food-Web, Migration & Population-Band Runtime;
4. `MSWI-06` — Composite Entity Role Binding Runtime;
5. `MSWI-07` — Biological Components, Harvest, Embodied Modification & Lineage Integration;
6. `MSWI-14` — Systemic Site/Scene Variant, Template & Promotion Integration;
7. `MSWI-18` — Systemic Coverage Diagnostics, Golden Proof & SMB-08 Handoff.

Stable sparse IDs are intentional. `MSWI-01` remains the family start/rotation gate and `MSWI-18` remains the family golden/SMB-08 gate, so no roadmap-DAG milestone rewrite is required merely because internal tranches collapsed.

## 2. Family purpose after reduction

MSWI is the **cross-domain consequence orchestration and persistent-world-response layer**.

Its defining question is:

> When an accepted Event or owner-domain change occurs, which other governed domains are allowed to respond, through which typed routes, with what attribution, reversibility, visibility and persistent presentation?

MSWI does not become a second World, Environment, Character, Creature, Organization, Project, Economy, Profession, Map, Scene, Action/Event or content-definition ledger.

It owns only the integration state and adapters that cannot sensibly live inside one source domain.

## 4. Canonical distinctions

The following distinctions are mandatory.

- reusable rule/profile definition vs live Campaign owner state;
- source Event vs downstream consequence Event;
- owner canonical state vs MSWI projection/receipt;
- proposed/dry-run route vs validated owner operation vs committed result;
- source-domain change vs systemic fan-out;
- direct consequence vs delayed consequence;
- reversible owner mutation vs compensating operation vs irreversible result;
- aggregate/cohort projection vs persistent individual identity;
- canonical location identity vs current/historical/alternate presentation variant;
- generated ephemeral/proposed site state vs accepted persistent Campaign state;
- resource/asset provenance vs world-state provenance;
- objective truth vs participant knowledge/visibility;
- cross-system diagnostic graph vs canonical gameplay truth.

MSWI may persist integration metadata and receipts, but may never copy mutable canonical owner state merely to make routing convenient.

## 5. Core contracts

### 5.1 `SystemicTransformationProfileDefinition`

Reusable definition describing which owner-backed dimensions may participate in one class of persistent world transformation.

Minimum semantics:

- stable profile ID/version;
- applicable Campaign/World/Environment/Location scope kinds;
- referenced owner dimensions only;
- threshold/milestone definitions;
- allowed source Event/change tags;
- eligible consequence-route references;
- reversibility/recovery class;
- visibility/discovery policy;
- multi-resolution policy reference where applicable;
- provenance/source/pack scope;
- compatibility/migration version.

A profile does not store canonical weather, ecology, settlement, economy, organization or resource truth.

### 5.2 `SystemicTransformationProjection`

Read-only integration projection over exact owner versions.

It may expose:

- scope and owner refs;
- profile/version;
- source dimensions with owner/version references;
- current qualitative/quantitative bands exactly as supplied by owners;
- crossed or projected milestones;
- unresolved dimensions;
- visibility-filtered explanation atoms;
- provenance/version.

It is stale when any required owner version changes.

### 5.3 `ConsequenceRouteDefinition`

Reusable MRCS/owner-authored route declaring how an accepted source Event/change may create candidate downstream owner operations.

Minimum semantics:

- route ID/version;
- source owner/domain and eligible Event/change tags;
- required source facts and versions;
- target owner/domain;
- applicability predicates;
- target operation definition/reference;
- transformation/mapping rule;
- deterministic/seeded/GM-adjudicated method class;
- route depth/hop policy;
- cycle/deduplication key policy;
- reversibility/compensation mapping;
- visibility/explanation policy;
- failure/blocked behavior;
- provenance.

A route never grants the target operation authority it does not otherwise possess.

### 5.4 `SystemicConsequenceEnvelope`

One bounded evaluation of possible downstream responses to a source Event/change.

Fields include:

- correlation/envelope ID;
- Campaign/scope refs;
- source Event/change ref and owner version;
- exact route versions considered;
- candidate target operations;
- blocked/unresolved routes and reasons;
- cycle/deduplication decisions;
- visibility-safe explanation atoms;
- deterministic seeds where required;
- expiry/staleness data;
- preview status.

The envelope is proposal/diagnostic state, not proof that downstream consequences occurred.

### 5.5 `SystemicPropagationReceipt`

Records one committed fan-out pass.

Minimum semantics:

- source Event/change;
- envelope/route versions;
- each attempted target owner operation;
- validated/committed/rejected/blocked status;
- resulting owner Event IDs and versions;
- compensation/recovery links;
- hop depth;
- deduplication/cycle evidence;
- delayed-follow-up refs;
- visibility-safe explanation projection;
- replay/provenance metadata.

### 5.6 `EcologySystemicProfileDefinition`

MSWI ecology uses accepted MNCS/Environment/World facts and Packet-06 resolution semantics.

The profile may declare:

- habitat suitability inputs;
- population quantity class: exact/range/band/distribution/unknown;
- carrying-capacity rule references when authored;
- succession stage definitions;
- food-web/dependency links;
- migration/territory pressure rules;
- harvest/overhunting/resource-pressure hooks;
- invasive/introduced-species hooks;
- extirpation/extinction/recovery/restocking/conservation transitions;
- aggregate transition references;
- uncertainty propagation;
- provenance/version.

There is no universal ecological equation.

### 5.7 `CompositeRoleBinding`

Binds one stable canonical entity identity to multiple governed roles without copying state.

Required semantics:

- canonical entity ref;
- role owner/type refs;
- per-role capability/interface refs;
- ownership/control/custody refs;
- role-specific permissions;
- shared versus role-local state references;
- compatibility constraints;
- role activation/removal/transition rules;
- provenance/version.

Examples may include creature+mount, creature+vehicle, sentient ship+NPC, living base+location host, or other source-supported combinations.

### 5.8 `BiologicalComponentIntegrationBinding`

Shared component/lineage contract used by both harvest and embodied modification.

It references rather than duplicates:

- source-authored anatomy/component definitions;
- component condition/damage state;
- harvest/capture/removal Event;
- donor/source lineage;
- quality/conservation state where defined;
- compatibility and body-location rules;
- downstream crafting/cooking/alchemy/medicine/research/economy targets;
- graft/implant/symbiote/prosthetic binding;
- grants/removals/retained-state/reversal behavior;
- optional identity/memory/psychological/social consequence rule refs only when explicitly authored;
- provenance/version.

No absent organ, yield, donor effect or psychological consequence is invented.

### 5.9 `SystemicVariantBinding`

Connects accepted systemic state to a canonical site/location/Scene presentation without cloning identity.

It includes:

- stable canonical place/site ref;
- relevant owner state/version refs;
- variant/template rule refs;
- MCS/MAS/MSAS/MCCS/ARI presentation binding refs as applicable;
- current/historical/alternate mode;
- visibility/fog policy;
- generated candidate seed/provenance when procedural assembly is used;
- ephemeral/proposed/persistent status;
- GM/owner promotion receipt when persistence is accepted;
- migration/version compatibility.

### 5.10 `SystemicCoverageReport`

MSWI-specific interpretation over PCA-12/Packet-08 graph/run evidence.

It may report:

- declared source capability/Event;
- valid consequence routes;
- fan-out depth;
- blocked routes;
- missing integrations;
- cycle candidates;
- duplicated route candidates;
- owner-domain coverage categories;
- intentionally terminal routes;
- visibility-safe explanation;
- exact graph/rule/profile versions.

It must never fabricate a mechanic merely to increase interaction density.

## 6. Consequence execution pipeline

The shared pipeline is:

1. **Accept source truth** — start only from a committed owner Event/change or an explicit preview source.
2. **Compile scope** — resolve Campaign, World/Location, involved owners, visibility and exact owner versions.
3. **Select routes** — load applicable `ConsequenceRouteDefinition` versions.
4. **Apply permission/knowledge filtering** — unauthorized/hidden data is excluded before route evaluation and explanation.
5. **Build dry-run envelope** — produce target-operation candidates, blocked routes and cycle/deduplication decisions.
6. **Validate each target owner operation** — target owners independently validate authority, stale versions, resources, prerequisites and domain rules.
7. **Commit accepted target operations** — canonical owners create their own Events/state changes.
8. **Record propagation receipt** — link exact source/target Events, rules and versions.
9. **Evaluate bounded further fan-out** — only routes/profile depth explicitly allowing another hop may continue.
10. **Schedule delayed follow-up** — Project/Time/Event owners handle future consequences.
11. **Refresh presentation projections** — maps/scenes/audio/UI consume accepted new owner state; presentation never back-writes truth.

## 7. Cycle, conflict and deduplication semantics

Systemic responsiveness must not create infinite mutation loops.

- Every automatic route has a stable deduplication key derived from source Event/change, route version, target scope and reaction phase or equivalent owner-safe identity.
- A consequence Event does not automatically re-trigger the same route chain unless the profile explicitly permits another semantic phase.
- Repeated routes that target the same owner operation are coalesced only when that owner explicitly supports aggregation; otherwise they remain separately inspectable candidates.
- Competing target operations are passed to the owner conflict policy; MSWI does not choose silently.
- If two routes would create contradictory world effects and no owner/rules precedence exists, the envelope reports unresolved conflict.
- Diagnostic cycle detection may block auto-commit even when individual operations are valid.

## 8. Reversibility, recovery and rollback

MSWI distinguishes:

- **inverse owner operation** — authoritative owner supports a true reverse operation;
- **compensation** — a later operation mitigates or offsets the result without claiming history was erased;
- **restoration workflow** — Project/Time or domain-specific work repairs/rebuilds/repopulates state;
- **irreversible result** — no automatic undo exists;
- **projection rollback** — discard uncommitted preview/proposed state only.

Rollback of an MSWI receipt never deletes canonical source/target Events.

## 9. Multi-resolution and autonomous-world rules

Packet 06 applies directly.

- ecology/population state may be aggregate, cohort, individual or adaptive-mixed only where the owning profile supports it;
- aggregate state is not a hidden population of invented individuals;
- refinement does not invent past personal Events;
- persistent identities never collapse back into anonymous nonidentity;
- exact/range/band/distribution/unknown certainty is preserved;
- no unit is double counted across aggregate and individualized representations;
- Campaign time, not wall-clock time, drives change;
- autonomous/offscreen consequences use owner-approved aggregate operations and Packet-03 autonomy rules;
- performance budgets may reduce detail but never grant mutation authority.

## 10. GM/player/creator UX

MSWI reuses Packet-07 interaction semantics.

### Preview

A GM/creator may select a source Event/change and inspect:

- direct owner result;
- eligible systemic routes;
- target domains;
- blocked/missing routes;
- expected reversibility;
- visible presentation changes;
- delayed consequences;
- uncertainty and unresolved facts.

Preview does not mutate canonical state.

### Commit

Commit requires the underlying source Event/change or explicit authorized owner operation. Every downstream owner remains independently validating.

### Explain

Role-safe explanations may answer:

- what changed;
- which source Event caused the evaluation;
- which rules/routes applied;
- which owner committed each consequence;
- what remains unknown/blocked;
- whether more consequences are delayed;
- which presentation variant is currently selected.

Hidden route existence/counts must not leak through diagnostics.

### Intervention

GM intervention uses existing owner operations, profile/rule changes or explicit adjudication. There is no generic “set world state” escape hatch owned by MSWI.

## 11. Permission, visibility and knowledge

- Permission filtering happens before route counts, search, diagnostics, AI context and export.
- A player-visible transformation projection may omit hidden causal dimensions and hidden consequence routes.
- Ecology/population reports preserve uncertainty and hidden population partitions.
- Secret organization/religion/faction consequences remain hidden until information paths authorize them.
- Procedural candidate content can remain GM-only until promoted/revealed.
- Optional AI receives only permission-safe projections and remains advisory.

## 12. Versioning, migration and replay

Every persisted integration record references exact versions of:

- source Event/change;
- owner state projections used;
- transformation/ecology/variant profiles;
- consequence routes;
- GPR/MRCS/PCA schemas where applicable;
- deterministic seed/randomness receipt;
- target owner operations/Events;
- accessibility/presentation profile when consequence meaning depends on it.

Migration rules may update definitions/bindings prospectively but may not silently reinterpret historical Event receipts. Replay must either reproduce the declared deterministic result under the same versions or report version incompatibility explicitly.

## 13. Failure and edge cases

Required handling includes:

1. stale owner version during preview/commit;
2. source Event later revealed to have been only a proposal;
3. route points to unavailable/disabled target capability;
4. target operation is unauthorized despite route applicability;
5. two routes create contradictory target requests;
6. cycle is detected across two or more owner domains;
7. delayed consequence becomes stale before execution;
8. ecology quantity is a band/range rather than exact;
9. carrying-capacity or food-web rule is absent;
10. introduced species has no authored interaction rule;
11. composite role becomes incompatible after form/state change;
12. one role is removed while others remain;
13. anatomy/component definition is partial;
14. harvest Event lacks method/quality semantics;
15. donor lineage is known but compatibility rule is absent;
16. embodied modification has no authored psychological consequence;
17. canonical place has no matching presentation variant;
18. procedural site generation produces an invalid candidate;
19. proposed site is discarded after preview;
20. hidden route would leak through fan-out count;
21. diagnostic score tempts creation of unjustified mechanics;
22. recovery is compensating rather than true inverse;
23. aggregate refinement would double-count individuals/resources;
24. migration/version mismatch prevents deterministic replay;
25. paid/cloud/AI provider is unavailable.

All fail safely: blocked, unresolved, GM-review-required or provider-off deterministic behavior as appropriate.

## 14. Accessibility contract

- Meaningful world change cannot depend solely on color, animation, audio or visual map comparison.
- Before/after state supports textual/semantic comparison.
- Diegetic timing information retains non-audio equivalents through MSAS/GPR/Accessibility owners.
- Graph/diagnostic reports expose accessible tabular/text alternatives to visual node-link diagrams.
- Dragging/precision pointing is not the sole way to review or promote generated candidates.
- Uncertainty and blocked routes are encoded semantically, not only by style/color.

## 15. Golden vectors

The final MSWI golden battery must include at least these vectors.

1. barren→habitable transformation with explicit source attribution;
2. pollution restoration with a reversible threshold;
3. irreversible transformation requiring compensation rather than undo;
4. source Event produces resource, hazard and travel consequence candidates;
5. one target owner rejects a candidate while others commit;
6. two-route cycle is detected and automatic recursion stops;
7. delayed consequence executes later through Project/Time/Event authority;
8. hidden route does not leak through player-visible route counts;
9. ecology habitat suitability changes population band without exact invented count;
10. overharvest causes attributable decline/migration pressure;
11. invasive-species rule is absent and remains unresolved rather than invented;
12. recovery/restocking/conservation path is attributable;
13. aggregate ecology refinement excludes individualized creatures from the aggregate remainder;
14. one living entity binds creature+mount+vehicle+base roles under one identity;
15. role removal does not delete the canonical entity;
16. form change invalidates one role and yields an explicit compatibility conflict;
17. source-authored component damage changes harvest availability;
18. harvest lineage flows into a governed crafting/research material;
19. graft preserves donor/source lineage;
20. graft without compatibility rule remains unresolved;
21. embodied modification reversal preserves explicitly retained state;
22. doctrine change occurs through Religion/Culture/Organization owners and MSWI routes only the accepted consequences;
23. profession/downtime loop executes in DPL/GPR/Project and MSWI consumes the result without a second schedule ledger;
24. pursuit resolves through GPR and produces a world consequence without an MSWI pursuit engine;
25. performance timing resolves through DPL/MSAS/GPR with an accessible equivalent;
26. grand Project milestone commits through Project authority and then fans out through MSWI;
27. procedural site candidate is deterministic from declared seed/profile;
28. procedural site remains ephemeral until explicit promotion;
29. promoted site retains canonical place identity and provenance;
30. current/historical map/scene variants show accepted world states without cloning the location;
31. transformation Campaign template configures primitives without creating a new runtime fork;
32. interaction coverage report finds a valid fan-out route;
33. coverage report identifies a deliberately missing route without inventing one;
34. coverage report identifies a cycle candidate;
35. diagnostic output is permission-filtered;
36. exact-head golden proof succeeds provider-off and optional AI remains nonauthoritative.

## 17. Reduction safety conclusion

The 18→7 reduction removes standalone work only where one of these is true:

- multiple baseline tranches share the same concrete implementation kernel;
- PDCP already closed the non-code design burden;
- another existing/future owner clearly owns the generic runtime or canonical state;
- only a small MSWI consequence adapter/proof remains, and it has been mapped to a surviving tranche.

No accepted capability, owner boundary, golden proof, accessibility requirement, permission/privacy rule, recovery/migration obligation or provenance requirement is deleted.

MSWI remains `owner_approved_planned` with `implementation_authority=false` until a future OPS3 governed start.
